## 0. The big finding — the export contains TWO products
1. **OZee CRM v2** (internal app + supplier portal + client approvals) — what the user asked for. Mocks: Design Guide, OZee CRM Inbox, OZee Admin Console (agency-workspace half), SignatureBlock.
2. **"Client OS"** — a *new* SaaS product the design team planned in `Client OS Product Plan.dc.html`: *"It ships as its own product — separate login, its own name — but it looks and behaves like the OZee CRM."* Its modules (nine, ranked by lock-in): Email signature builder (P1, "start here"), Leads & inbox (P1), Scheduling (P1), Domain & DNS (P1), Agency hub (P1 — the client-facing view of *our* work: approvals, assets, tickets), Jobs & invoicing (P2), Results dashboard (P2 — the SEO Reports screen), Social planner (P3), Automation & AI (P4). Plus a **platform layer** (Admin Console "Workspaces / Plans and entitlements / Platform team"): OZee sells the same product to other agencies under Studio/Agency/Network plans with white-label and support-access switches. Mocks: Home A/B (these are the *client tenant's* home — "Harper & Vale", enquiries/bookings/signatures — not the internal "My work" the guide table claims), Client Board, Client OS Login/Home/Announcement/SEO Reports, Signature Builder/Studio/Suite, and the platform half of Admin Console.

The user's instruction "whatever is available in design is in scope" therefore needs a decision, because Client OS as drawn is a year-long product roadmap in its own right (the Product Plan says so: "roughly a year end to end").

## 1. Recommended scope decision (adopted as plan v1.1 unless the user overrides)

| Layer | R1 (this plan's Phases 0–7) | R2+ (07-deferred, new "Client OS" programme) |
|---|---|---|
| Internal CRM | everything in 01–05 **plus** the Admin Console's agency-workspace model (below) | Workspaces / Plans / Platform team / white-label (multi-tenancy for *other agencies*) |
| Client-facing | **Agency hub** = the client portal already in the plan (03 §3.8): Login, Home (Today feed), approvals/deliverables, documents, tickets (client-raised tasks), invoices, announcements, **Results/SEO reports** (screen exists), Client Board as the per-client shared workspace | Signatures product, Enquiries/lead capture with SMS, Scheduling/calendar booking, Domain & DNS client self-service, Jobs & invoicing for the client's own business, Social planner, Automation & AI |
| Schema | **tenant-ready from day one**: `workspace_id` on every business table (D19), `businesses` layer, `roles.level`, tiers, guards, access requests, ghost sessions, audit, teams, domains registry, service packs, payment terms | plan entitlements, white-label config, platform identities, signature/booking/enquiry tables |

Rationale: the client portal, Admin Console workspace model and finance rules are directly needed by OZee's own operation and the legacy data maps onto them; the Client OS product modules have **no legacy data and no backend**, and the Product Plan itself lists four unresolved "open calls" (own login vs guest seat, registrar choice, sell signatures alone or not, who pays SMS). Building them now would delay the migration the user asked for. Adding `workspace_id` now costs one column + a global scope; adding it later costs a second migration of every table.

**ADR-0002** records this. **Open questions for the user (answer before Phase 1 ends):** (1) confirm the split above; (2) if Signatures must be in R1 as the "wedge", it is a self-contained module (`Modules\Signatures`, ~4 weeks: templates, brand kit, employees directory, Suite-level studio, Gmail signature push, copy-HTML export) — say so and it becomes Phase 4b; (3) registrar for Domain & DNS sync (Cloudflare vs Namecheap) — R1 keeps a manual registry only; (4) Home: internal "My work" uses Home B's layout with internal data; Client OS Today uses Home A's hero-card queue (survey recommendation) — confirm; (5) Client OS accent: identity blue `#eceffa/--ozee-blue` (mocks) vs working blue (guide) — confirm.

## 2. What the Admin Console adds to R1 (agency-workspace model) — spec summary, details in `survey/design_screens_internal.md §5.5`
The console encodes a **three-ceiling permission system**: *plan entitlement* (workspace ceiling) → *client/project tier* (Care < Growth < Partner; per project, business/client show the strictest) → *role & level* (0 none, 1, 2 team lead, 3 department head, 4 workspace owner; nobody grants above their own level). Actions form a **19-item matrix** grouped by module (Signatures, Domain & DNS, Website, Social/SEO/Ads, People & access, Client data & billing) with **guards**: Approval (creates an access request for an approver of sufficient level), Re-auth (password/2FA re-prompt), Logged, Reason (ghost), Ceiling. Tier blocks: Care blocks `dns-edit, dns-move, sig-campaign, soc-publish, ads-budget, bil-change`; Growth blocks `dns-move, bil-change`.

R1 adopts it as follows (schema deltas in 02 addendum §A):
- `workspaces` (one row "OZee" in R1; `workspace_id` on all business tables; global scope; platform screens hidden).
- `businesses` (a client owns/co-owns several; projects, domains and contacts hang off a business) + `business_contacts` with relationship (Account owner, Joint owner, Billing contact, Franchise holder) and status (Live, Onboarding, Paused). **Naming: use `businesses` (mock vocabulary), not `organisations`.**
- `projects.tier` (care|growth|partner, default care), `roles.level` (0–4), `permissions` table becomes the **actions catalogue** (`module`, `guard`) seeded from the matrix; `role_permission` gains `granted|denied` overrides; `Permissions::can(user, action, client)` implements the three-ceiling check + tier blocks; guards implemented in `Access` (approval → `access_requests`; re-auth → `sudo` middleware; logged → activity_log; reason → `ghost_sessions`).
- `teams` (colour, lead, `lead_manages`, `modules[]`) + `team_members` (Team lead / Senior / Member / Contributor) + `team_clients` (reach); staff inherit every client their teams serve; contractors get named clients via `access_grants` with mandatory `ends_at` (≤90 days, extension = request), 2FA required.
- `project_contacts.reach[]` (Approve deliverables · Comment · Weekly report · Billing · On the contract) replaces the single `role` enum; billing contacts receive invoices; approvers are the deliverable approver options.
- `service_packs` (Website / SEO / Google Ads / Signature / Social) with milestone→scope-item→task skeletons; `CreateProject` from packs scaffolds; "Duplicate a project" shifts dates.
- `deliverable_versions` (v, submitted_at, by, state Approved | Revisions requested | Waiting on {approver}, note) + `deliverables.visible_to_client` + `approver_contact_id`.
- Finance rules: budget = Σ expendables converted to AUD at the daily rate (never typed); proposals approvable only if `amount ≤ service budget − committed`; accepted proposal adds the contractor to the project team; bills: `Needs coding` (missing Xero account/tax) → `Awaiting approval` (chain by AUD size: ≤$1k team lead; >$1k + department head; >$5k + workspace owner) → `Ready to sync` → `Synced to Xero` → `Paid` | `Rejected`; GST = amount/11 for "GST on expenses (10%)"; invoices raised only from a service's **payment terms** (percent splits with presets 100 · 50/50 · 30/30/40 · 40/30/30 · thirds · quarters; labels Full payment / Deposit / Payment n / Final); raised terms cannot be picked again; part payments from the **bank feed** leave a balance; FX table AUD/USD/PKR "as of" timestamp; Xero expense accounts 6120/6130/6200/6300/6400; paid-from accounts list. → these refine 03 §3.6 (service_milestones = payment terms; `bills.status` gains `needs_coding`, `ready_to_sync`, `synced`; `bank_transactions` = bank feed).
- Domains: `domain_providers` (Registrar | DNS host | Registrar + DNS; API connected or manual; daily sync 06:00 AWST), `domains` (business nullable, teams reach, registrar, expiry ≤60 days flag, auto-renew, SSL status, use), `dns_records` (A/CNAME/MX/TXT/NS, TTL set, `locked` for MX/NS/SPF/DMARC → approval by L3, previous value kept 90 days). R1 = registry + manual records; provider APIs R2.
- People: `users.engagement` (Employee | Contractor), admin level = `roles.level`, contractors `access_ends_at`, seats counted while live.
- `access_requests` (who, action, client, reason, approver ≥ need, approve / send back), `ghost_sessions` (read-only by default; elevation = one task, 15 min, reason, client owner emailed; billing & domain transfer never; events Opened/Read/Elevated/Write), `audit` viewer (7-year retention, per-client CSV export, tags Logged / Reason given / Re-auth / Blocked / Ceiling checked / Expiry).
- Admin console = 28 screens (`survey/design_screens_internal.md §5.5.3` route table) → tickets in 05 addendum. It is desktop-only (designed at 1560px); uses text-labelled rail items and a 236px secondary sidebar — treat as the Admin area's contextual sidebar (04 §4).

## 3. Client-facing R1 (Agency hub) — from Client Board + Client OS mocks
- **Client Board** (`survey/design_screens_internal.md §5.4`) is the per-client/per-project shared workspace with a **Client / OZee-team view toggle**, business & project switchers, five tabs: **What's new** (activity feed with dual-audience copy), **Board** (kanban with *Requests* and *Waiting on client* columns and triage: Accept / Quote / Hold / Ask for something), **Deliverables** (checklist + material requests + files + ideas; "File to deliverable"), **Emails** (per business), **Support tickets** (client-raised, NEW module — map to tasks with `origin=client_portal` + `kind=ticket`), task drawer with structured asks, one compose modal with five variants (Reply / Ask for something / Turn into a task / Send / Resolve). Staff see it at `/contacts/{id}/board`; clients see the same component under `/client/...` with the client view forced. Requests = `enquiries` + inbound client emails (both feed the Requests column).
- **Client OS Login** (`§5.7`): passwordless 4-step (email → 6-digit code cells → optional password → done), social providers (Google/Microsoft/LinkedIn — R1: Google only, others hidden), "saved device". Maps to Access `client_sessions` + `one_time_codes(purpose client_verify)`.
- **Client OS Home** (`§5.8`): role-specific hero (owner sees revenue; manager doesn't), action cards, quiet stats, "agency work" panel, jump links; empty copy "You're all clear" / "Ticking along without you". Feed item types listed in §5.8 → `client_feed_items` query composed from approvals, deliverables, invoices, announcements, tickets.
- **Announcement** (`§5.9`): one modal, three kinds (feature / promotion / approval) with media slot → `announcements(kind, media attachment, cta)`.
- **SEO Reports** (`§5.11`): overview (5 KPI tiles, AEO/GEO card, combo chart, rank bands + keyword table, GBP, Core Web Vitals, cost per lead, data sources, work in flight, archive) + monthly report view + "Ask about this" question modal (→ creates a ticket/comment) — R1 renders from `seo_reports.data` JSON with a documented schema (`survey §5.11 backend`), all charts via `OzeeChart`; data ingestion stays manual/API upload.
- **Rail (canonical Client OS):** Today · Enquiries (R2, hidden) · Calendar (R2, hidden) · Signatures (R2, hidden) · Domain (R2, hidden) · Results · OZee (agency hub: approvals, deliverables, tickets, documents, invoices) · People (R2) · Settings. Hidden items are feature-flagged so the R2 modules slot in without redesign. Dark mode is not designed for Client OS — R1 ships light only there (internal app is light+dark).
- **SignatureBlock** fragment = the email signature renderer used by Comms (4 layouts; pick the logo variant, not initials).
