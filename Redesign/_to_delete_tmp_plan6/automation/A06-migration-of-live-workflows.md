# A06 — Migrating the live workflows (legacy WF8–WF28 → v2)

Source of truth for each legacy workflow: `../survey/automation_deep.md §13` (step-by-step reconstruction, defects, model flags). Rule: **re-author from intent, never copy configs** — the legacy configs contain corrupted references (WF17), literal FK ids, legacy model names, SQL literals and secrets. Each v2 workflow is authored in the builder (or as a template JSON in `Database/Seeders/Templates/*.json`) against v2 models/events/actions, then verified with the recorded sample payloads.

## 2. Shared conventions ported
- "Support" milestone: `milestones.is_support` per project (unique) — actions `work.create_task` default to it when no milestone is given.
- System sender `sender_id = 1` → the workflow actor + the workspace default mailbox; `ai_lead_outreach_template` → `email_templates.slug ai_lead_outreach` (migrated in master 06 §4.8).
- Task type literals (2 = QA, 4 = follow-up) → `task_types.slug` `qa`, `follow_up` seeded; templates reference slugs.
- `Context` memory → `comments(kind note, visibility internal)` on the contact with `source automation`; prompts receive `contact.notes` via the relationship picker; a nightly `ai.summarise` compaction keeps the last 20 notes + one summary note.
- Morph literals (`App\Models\Lead`, `client`) → aliases `contact`; conditions on `sender_type == client|lead` → `thread.contact.stage == client|lead`.
- Prompts: the 18 legacy prompts are imported into the Ai library as version 1 with their response schemas (from `response_json_template`), renamed to unique names (the duplicated ids 2 and 8 become separate prompts), and re-pointed to v2 variable names; a prompt drift report lists inputs that referenced legacy fields.

## 3. Data migration of the automation tables themselves
- `workflows`/`workflow_steps`/`prompts` → **archived** raw (`legacy_workflows`, `legacy_workflow_steps`, `legacy_prompts`) per master 06 §4.11; plus `automation:import-legacy --dry` produces, for each legacy workflow, a *draft* v2 workflow via the transformer (event names remapped, `:`→`.`, `step_N`→keys by name, morph literals → aliases, model/field names via the mapping table, `NOW()`/`TODAY()` → filters, unknown fields listed as issues). Drafts are for reference/comparison only; the templates in §1 are what gets published. Executors compare the transformer's draft with the template to catch forgotten rules.
- `execution_logs` (≥ thousands of rows with full contexts and PII) → **not migrated** into runs; archived raw for 90 days then dropped. `automation_daily_stats` is back-filled with counts per legacy workflow per day for the history chart.
- `schedules` rows for workflows → `workflow_schedules` on the corresponding template instance (cadence preserved; timezone Australia/Perth).
- Secrets found in `step_config` (BugHerd key, addresses) → `credentials` (`bugherd`) created by the user at cutover; the key is **rotated** (it was committed to git).

## 4. Built-in templates (seeded, also offered in the Hub)
The ten above plus generic starters: "Notify team lead when a task is blocked", "Escalate thread past SLA", "Create standup reminder", "Weekly project digest", "Client review reminder after 3 days", "Invoice overdue nudge" (finance, L3), each with capability list and sample payload.

## 5. Verification (ticket AU-MIG-04)
For every template instance: (1) replay 5 recorded legacy trigger samples (converted payloads) as **dry runs** → expected effects listed in a fixture (`tests/Fixtures/automation/expected/<template>.json`); (2) a live shadow week before cutover where templates run in `dry_run` mode against the migrated v2 DB copy and the effects diff against what the legacy workflows did in the same period (from `execution_logs`) is reviewed; (3) sign-off checklist per template in the migration report.
